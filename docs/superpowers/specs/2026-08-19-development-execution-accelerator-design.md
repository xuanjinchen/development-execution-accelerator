# 开发执行加速器设计

## 状态

- 日期：2026-08-19
- 状态：已确认
- Skill 名称：`development-execution-accelerator`
- 定位：消费既定开发决策并优化执行与验证链路的通用 Agent Skill

## 背景与定位依据

项目开发中的耗时不只来自任务规模，也来自串行等待、重复读取、重复构建、过早运行全量测试、并发写入冲突和失败后重跑过多工作。该 Skill 应在所有进入执行阶段的项目开发任务中触发，让小任务保持低开销，让具备独立工作面的任务安全并行，并以最小充分验证缩短反馈时间。

本 Skill 不承担项目规划或架构决策。调研确认已有开源方案覆盖这些职责：

- GitHub Spec Kit（MIT）提供 `plan`、`tasks` 和按计划实施的规格驱动流程。
- Superpowers（MIT）提供 `writing-plans`、`executing-plans` 和按计划分派任务的开发方法。
- OpenSpec（MIT）提供面向多种 AI 编码助手的规格驱动流程。
- Taskmaster 公开提供任务与依赖管理，但其 GitHub 元数据未给出可确认的 SPDX 许可证，因此不作为开源结论的主要依据。

这些项目足以证明项目规划器已经存在。开发执行加速器只接收上游 Skill、用户或项目规则已经确定的任务、依赖和验收要求，并在不改变决断的前提下优化执行顺序、并发、等待利用和验证范围。

## 目标

1. 对所有已进入执行阶段的软件项目任务提供自适应提速，不要求用户显式提及性能或长任务。
2. 在支持并行工作者或后台命令的 Agent 中减少可避免的墙钟等待时间。
3. 在不删减必跑检查的前提下，优先执行最小充分验证，缩短首个有效反馈时间。
4. 在能力较弱的 Agent 中安全降级，仍通过关键路径优先、上下文复用和精准验证获得收益。
5. 保持实现结果、架构边界、功能范围和验收标准与上游执行契约一致。
6. 以配对行为评测证明正确性不下降且至少一个核心速度指标优于无 Skill 基线。

## 非目标

- 不选择技术架构、框架、存储、公共接口或模块边界。
- 不把模糊需求扩展成产品方案，不替代需求分析、头脑风暴、架构设计或实施计划 Skill。
- 不改变既定任务的业务含义、验收标准、文件边界或必跑验证。
- 不为了制造并行度拆分强耦合修改，不允许多个工作者无协调地修改同一冲突域。
- 不宣称所有 Agent 都具备相同工具，也不把协议兼容描述为已经真实验证的正式支持。
- 不实现常驻守护进程、远程任务平台、构建系统或新的项目级缓存。
- 不默认安装全局规则、修改用户配置、发布包或创建公开 Release。

## 触发语义与协作顺序

### 应触发

只要软件项目任务已经具备可执行方向，本 Skill 都应作为执行优化层触发，包括编码、修复、重构、测试、迁移、构建配置、仓库文档和其他会产生项目交付物的任务。用户无需提及“提速”“并行”或 Skill 名称。

### 不应单独触发

- 请求仍处于方案探索、架构选择或项目任务规划阶段。
- 纯解释、纯代码审查、状态查询或不需要执行项目工作的请求。
- 用户明确要求逐步演示、串行观察或禁止并行的任务。
- 上游决断存在会改变公共行为的缺口，且无法从既定计划或项目规范中解析。

### 与其他 Skill 的关系

领域 Skill 决定“做什么”和“按什么规则做”，本 Skill 只决定“怎样更快地执行已经确定的工作”。它在规划或架构 Skill 完成后运行，并可与调试、测试、前端、文档和代码注释 Skill 同时生效。发生冲突时，上游业务与架构约束优先；本 Skill 缩小或关闭加速策略，不改写上游决断。

## 输入执行契约

Skill 从会话、已批准计划、项目规则和用户要求提取执行契约。可获得的字段包括：

- 既定任务及完成条件。
- 已知依赖顺序和不可并行约束。
- 允许修改的文件或模块范围。
- 必须保留的接口、行为和兼容要求。
- 必跑测试、构建、格式化、安全或交付门禁。
- 当前工作区状态和不属于本任务的现有改动。

正式计划不一定以结构化文件存在。对于明确的小任务，用户要求、项目就近规范和现有实现共同构成最小执行契约。Skill 可以从这些证据确定执行顺序，但不能引入新的架构选择。

若缺失信息只影响调度，可采用最保守的顺序执行。若缺失信息会改变接口、业务行为、模块边界或验收口径，Skill 必须把问题交回负责规划或架构的上游 Skill；无法调用上游时只提出一个阻塞问题。

## 能力模型

Skill 以能力而不是产品名称选择加速策略。启动时只检查本次任务需要的能力，并在本次运行中复用结果：

| 能力 | 用途 | 不可用时的降级 |
| --- | --- | --- |
| 独立工作者 | 并行执行无依赖的调查、实现或复核 | 主 Agent 按关键路径顺序执行 |
| 定向通信 | 给运行中的工作者补充约束或结果 | 等待边界后重新派发最小任务 |
| 后台命令 | 隐藏构建、下载和测试等待 | 前台运行并停止启动依赖任务 |
| 增量输出与等待 | 在长命令期间获得进度且避免忙轮询 | 使用有界超时并在完成后读取结果 |
| 计划或状态工具 | 记录就绪、运行、完成和失败状态 | 在当前上下文维护紧凑执行账本 |
| 原生构建缓存 | 复用项目认可的编译和依赖缓存 | 不自行创建跨任务缓存 |

通用核心只依赖读取文件、修改文件和运行命令。平台适配材料只描述能力映射，不复制业务规则。某个 Agent 只有完成实际发现、调用和输出验证后才能列为正式支持；其他 Agent 只标注为协议兼容或实验性。

## 自适应执行链路

### 1. 锁定既定决断

先读取上游执行契约和工作区状态，列出不能改变的范围、依赖与验证。若任务仍需要架构选择，停止本 Skill 的调度决策并交回上游。

### 2. 建立轻量执行账本

把既定任务映射为就绪、运行、完成、失败或阻塞状态，并记录依赖、预期写入范围、验证需求与已有结果。此步骤只用于调度，不改变任务含义，也不为小任务创建持久文件。

预计跨会话或上游已经要求持久计划时，复用上游状态载体；否则使用 Agent 自带计划能力或当前上下文。Skill 不在用户仓库中创建未授权的常驻状态目录。

### 3. 选择最低成本执行模式

#### 快速模式

当既定工作只有一个短关键路径、没有可安全重叠的等待或协调成本高于收益时，主 Agent 直接执行。快速模式不启动工作者、不生成额外计划文件，只做一次必要上下文定位并运行最小充分验证。

#### 并行模式

当执行契约中至少存在两个已经独立的工作面，且预期节省高于分派和整合成本时，按依赖波次运行。优先并行只读调查、独立模块实现、测试准备和独立复核。主 Agent 保留一个调度与整合槽位，完成一个工作面后立即补充下一个就绪任务，不等待整批工作全部结束。

#### 等待重叠模式

当长命令运行期间存在不依赖其结果的既定工作时，把命令放入后台，并继续这些工作。不得在依赖结果未知时提前执行依赖分支。相同命令、输入身份和工作区版本在同一任务中只保留一个有效结果。

### 4. 执行并发安全约束

- 每个潜在冲突域只允许一个写入负责人；冲突域至少包括同一文件，也可由上游计划定义为同一强耦合模块。
- 多个工作者需要同一上下文时，由主 Agent 提供最小共享事实，避免各自重复扫描完整仓库。
- 工作者任务必须包含目标、允许修改范围、完成条件和返回证据；不把架构判断委派给执行工作者。
- 不为填满并发槽位启动没有独立价值的工作，也不重复派发同一调查。
- 并发导致资源争抢、编辑冲突、结果波动或集成成本上升时，降低并发并保留已完成的独立结果。

### 5. 利用长命令等待

后台命令启动后记录命令、工作目录、输入版本和会话标识。等待期间只执行无依赖工作；按环境支持的等待机制获取增量结果，避免高频轮询。命令失败、超时或输出停滞时保留最小诊断证据，不以相同参数盲目重启。

### 6. 执行最小充分验证

上游要求的验证集合是不可删减下界。Skill 可以调整相互独立检查的执行时机和并行度，但不能把“尚未运行”写成“无需运行”。

在上游集合之外，验证按以下成本顺序选择：

1. 语法、格式、类型、静态契约和 diff 检查。
2. 与改动文件或行为直接对应的测试。
3. 受影响模块、包或服务的测试与构建。
4. 只有依赖传播、风险等级、项目规则或交付门禁要求时才运行全量验证。

能独立运行且不会争抢同一构建资源的检查可以并行。项目原生命令、测试映射和缓存优先；无法可靠识别影响面时采用上游规定或项目现有聚合命令，不猜测一个更窄但可能漏检的集合。

### 7. 形成最短失败回路

失败只阻塞依赖该结果的任务，其他独立工作继续。先定位最早失败阶段和最小影响范围，再修复并重跑受影响验证；只有共享基础、依赖图或交付门要求受影响时才扩大重跑范围。

若失败暴露新的架构或需求决策，停止执行优化并交回上游。若只是工具能力缺失，退化到顺序执行或项目标准验证，不把工具限制解释为业务失败。

### 8. 输出执行证据

最终报告保持紧凑，并根据实际情况包含：

- 完成的既定工作与交付物。
- 使用的快速、并行或等待重叠模式。
- 运行的验证及结果，明确区分必跑与补充验证。
- 失败、重试、降级和保留结果。
- 可获得的墙钟耗时、Token 与命令次数。
- 未验证能力、未执行检查及可验证原因。

没有同条件基线时不得宣称具体加速比；只报告采用了哪些消除等待或重复工作的机制。

## 资源与实现边界

### 核心文件

- `SKILL.md`：包含触发、输入边界、执行顺序、并发不变量、精准验证和失败处理。
- `docs/skill-brief.md`：保存版本化需求、验收标准、路径映射和增强轨道状态。
- `docs/decisions.md`：记录职责收窄、开源规划器调研、能力模型和兼容声明策略。
- `evals/evals.json`：保存正向、隐式、负向、边界、冲突和失败案例。
- `README.md`：说明安装、执行阶段用法、与规划 Skill 的关系、验证和移除方法。

### 渐进披露

当主 Skill 无法在聚焦预算内同时容纳多 Agent 能力映射和多生态验证规则时，启用 `references/`：

- `references/agent-capabilities.md`：能力探测、平台映射和降级原则。
- `references/validation-strategies.md`：Maven、Gradle、npm、Python、Go、Rust 等项目的影响面与项目原生命令选择原则。

主 Skill 只在相关能力或生态出现时读取对应资料。若核心正文足够短且清晰，则保持该轨道禁用。

### 确定性脚本

脚本不是首版默认依赖。只有至少两个独立评测重复实现同类机械逻辑，且脚本能降低耗时、Token 或错误时才启用。例如：

- 将上游提供的任务、依赖和写入范围转换为执行波次。
- 根据已知项目清单和改动路径生成候选验证阶梯。

脚本只输出建议或结构化数据，不自行改变架构、执行破坏性命令或扫描无关目录。无法证明收益时保留提示型核心，不创建脚本。

### 隐式触发

用户要求所有项目开发执行任务都可以触发，因此隐式触发是必需能力。先使用准确且积极的 description 评测标准发现是否足够；仅当真实评测证明标准发现仍不稳定时，才增加最小规则模板。规则只负责加载 Skill，不复制执行算法。

### 多 Agent

用户要求兼容多种开发 Agent，因此启用多 Agent 轨道。实现使用共享核心和薄能力映射。正式支持表按 Agent 独立记录版本、发现方式、调用方式和真实运行证据；缺少 CLI、登录或可复现运行条件的 Agent 保持实验性或阻塞，不影响通用核心交付。

### 安装与发布

首版不需要修改多个用户配置或共享规则，因此安装器保持禁用，使用标准 Skill 目录复制或 Agent 支持的本地 Skill 入口。用户未授权公开发布、Tag 或 Release，开源发布轨道保持禁用；仓库仍遵守脚手架许可证和安全规则。

## 评测设计

### 首轮三个配对案例

1. 核心正向：上游已确认两个互不冲突的实现任务和一个耗时验证，观察 Skill 是否安全并行并重叠等待。
2. 相邻负向：用户要求选择系统架构并拆分项目任务，观察 Skill 是否不越权接管规划。
3. 边界案例：Agent 不提供独立工作者或后台命令，观察 Skill 是否退化为关键路径顺序执行并保留必跑验证。

每个案例同时运行有 Skill 与无 Skill 基线，使用相同模型、输入、隔离仓库和输出要求。首轮运行开始后再根据验收标准补充客观断言，避免依据已看到的结果设计偏置评分。

### 扩展案例

- 单文件小任务：验证不会启动无收益的协调流程。
- 多模块并行任务：验证依赖波次和写入冲突控制。
- 构建密集任务：验证长命令重叠、项目缓存复用和精准测试。
- 架构缺口：验证交回上游且不生成新的设计决断。
- 验证失败：验证只重跑受影响分支并保留独立结果。
- 隐式请求：用户不提 Skill 或提速，仍在执行阶段加载。
- 纯规划或纯解释：验证不误触发执行链路。

### 指标与交付门

正确性是不可交换的硬门：所有上游验收标准和必跑验证必须完成，副作用、冲突和架构越权为零。只有正确性达到基线后才比较效率。

效率记录以下指标：

- 端到端墙钟时间与基线加速比。
- 首个失败或首个有效验证结果的时间。
- 小任务的 Skill 启动开销。
- 重复命令、重复仓库扫描和无效等待次数。
- 并发冲突、取消工作和重跑范围。
- Token 使用量及其与墙钟收益的交换。

初始成熟交付目标为：并行代表案例的中位墙钟时间至少降低 20%；小任务中位额外开销不超过基线的 15% 且绝对增加不超过 3 秒；同一输入身份的重复长命令为零；验收通过率不低于基线；不存在为了提速跳过的必跑验证。环境波动较大时使用至少三次采样并报告中位数和离散程度。

若真实模型或目标 Agent 运行需要凭据、付费调用或额外授权，确定性检查继续完成，对应兼容与速度结论保持阻塞，不用模拟数据冒充真实证据。

## 确定性测试

若评测证明需要脚本，则遵循测试先行，至少覆盖：

- 无依赖任务的波次安排。
- 链式和菱形依赖的关键路径。
- 循环依赖拒绝与上游反馈。
- 文件或模块冲突导致的串行化。
- 能力缺失时的降级。
- 必跑验证不可被候选验证覆盖或删除。
- 相同命令和输入身份的去重。
- 非法、缺失和超出范围的输入。

无脚本时仍使用静态契约测试检查 frontmatter、触发边界、正文必备语义、资源引用、评测结构、Token 预算和文档一致性。

## 安全、隐私与恢复

- 不运行上游未授权的破坏性、凭据、付费或发布操作。
- 不以提速为理由覆盖用户已有改动、强制重置工作树或扩大写入范围。
- 后台命令记录工作目录和身份，避免把结果错误归属到已经变化的工作区。
- 临时评测使用隔离目录和虚构路径，不读取或修改真实 Agent 配置。
- 日志只保留最小诊断信息，不输出凭据、完整用户配置或私人路径。
- 失败后保留可复用的独立结果；无法证明结果仍对应当前输入时将其判为失效，而不是错误复用。

## 交付与验证流程

1. 使用脚手架初始化独立 Skill 仓库并固化 Skill Brief。
2. 在正文调优前固定三个首轮行为案例。
3. 以 TDD 建立静态契约；只有证据满足时增加 references、脚本或规则模板。
4. 运行有 Skill 与无 Skill 的配对评测，捕获耗时、Token、输出和评分。
5. 生成标准评审页面，让用户检查行为输出和 benchmark；根据反馈迭代。
6. 对可获得的目标 Agent 逐个平台执行真实发现与运行验证，更新正式支持状态。
7. 运行 `npm run check`、脚手架交付门禁、完整 diff、未跟踪文件、敏感信息和代码注释审查。
8. 只交付本地可逆成果；未经明确授权不推送、不创建 Tag、不发布 Release。

## 完成标准

满足以下条件才可声明成熟交付：

1. Skill 在执行阶段的直接与隐式正向请求中可靠触发，在规划、架构和纯解释请求中不误触发执行链路。
2. 快速、并行、等待重叠、精准验证和能力降级均有行为或确定性证据。
3. 所有上游要求、文件边界与必跑验证保持不变，未发生架构越权或并发写入冲突。
4. 至少一个代表性并行案例达到速度门，小任务满足开销门；未达到时继续迭代或如实报告未成熟。
5. 通用协议与正式 Agent 支持范围明确分开，每项正式声明均有真实运行证据。
6. 脚手架 `check` 与 `gate:delivery` 通过，Evidence Contract v1 闭合。
7. README、Skill Brief、决策日志、评测和交付报告与实际行为一致。
8. 完整 diff、未跟踪交付文件、安全与注释审查完成，没有已知敏感信息或虚假能力声明。
